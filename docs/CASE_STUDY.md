# AURA LABS · 项目案例

**Agent V1.1（冻结）· Streamlit MVP V0.1 · Runtime Logging V0.1**

本项目为虚构护肤品牌的客服 Demo，覆盖知识问答、模拟订单/退款查询和人工处理建议。完整配置与历史记录见 [项目状态](../PROJECT_STATUS.md)，运行步骤见 [Running](RUNNING.md)。

## 1. 问题与方案

客服问题需要不同的事实来源和权限，不能都当作普通文本生成：

| 问题 | 处理方式 | 设计理由 |
|---|---|---|
| 产品价格、成分、物流与退货规则 | RAG | 根据企业资料回答，避免补写政策或未公开信息 |
| 指定订单在哪里、退款是否到账 | TOOL | 静态资料无法提供具体状态，必须查询 |
| 人工请求、投诉争议、当前无法执行的操作 | HANDOFF | 给出人工处理建议，不假装完成业务动作 |

“广州多久到”是通用规则，“订单 123456 到哪里了”是状态查询；划分依据是数据和权限，而非是否出现“订单”这个词。缺少订单号时请求补充，不凭空生成编号。

目标是交付可演示、可检查的应用链路，没有真实业务量、人力节省或商业收益数据。

## 2. 实现与关键取舍

**RAG：** 六份 Markdown 覆盖产品、退换货、物流、FAQ、成分和售后，形成 Chroma `aura_customer_service` 中的 122 个片段。切分按标题、段落、列表和完整句子组织，默认目标上限 600 字，不强制补足 300 字、不跨标题硬拼，无额外重叠；完整长句可超过目标上限。

本地 `BAAI/bge-small-zh-v1.5` 处理文档和查询，归一化后以 cosine 距离检索 Top 5，再将问题与片段交给 DeepSeek。片段带 `source_file`、`heading`、`chunk_id`、正文。没有可用片段时本地拒答；资料不足时不补写企业事实，医疗问题不诊断、不推荐药物。

**Agent：** Streamlit 与 CLI 共用 AgentService，由 DeepSeek 选择 RAG、Tool 或 HANDOFF，不使用关键词意图路由。知识路径复用 RagService，工具路径执行后回传结果，再由 DeepSeek 回答。

- `get_order_status`：查询模拟订单状态、物流公司、单号和最新位置。
- `get_refund_status`：查询模拟退款状态、金额和申请时间。
- 程序只执行白名单函数；订单号须为本次输入中的 6～20 位数字字符串，仅允许 `order_id`，校验不等于身份授权。
- 最多一轮工具执行，同轮最多两个调用；工具只读，不退款、不改订单、不裁决争议。

预置订单 `123456` 为运输中，退款仍在处理中、尚未到账；不存在的编号返回“未找到订单”。数据固定模拟，不随真实业务变化。

**技术选择：** BGE 和 Chroma 负责本地向量检索，DeepSeek（配置为 `deepseek-flash`）负责决策与生成；兼容 SDK 实际请求 DeepSeek，不调用 OpenAI 模型。直接 Python 模块足以覆盖一个知识库、两个工具和三条路径，因此没有引入 LangChain、LlamaIndex、多 Agent、GraphRAG、reranker 或混合检索。未做模型或 Top K 的系统寻优，不宣称当前组合最优。

完整流程和职责见 [架构说明](ARCHITECTURE.md)。

## 3. 怎样验证

评测分三层，使用确定性规则，不增加第二个 LLM 裁判：

| 层次 | 规模 | 检查内容 | 已保存结果 |
|---|---:|---|---|
| Retrieval | 80 条 | 预期来源是否进入 Top K | Top 1：64/80（80%）；Top 3：75/80（93.75%）；Top 5：76/80（95%） |
| RAG | 80 条 | 必含、禁含与行动规则 | 38/80，47.5%；API 成功 80/80 |
| Agent V1.1 | 40 条 | 路径、工具、参数及回答 | 路径 40/40；工具及参数各 20/20；HANDOFF 12/12；最终回答规则通过 39/40（97.5%） |

来源文件命中不代表取回了足够的规则，更不代表回答正确。RAG 的 47.5% 是规则通过率，42 条失败尚未全部人工复核，不能统一归因于评分器或模型。不同测试集的成绩不能互相替代。

RAG 的必含项用 `;` 分隔概念，组内 `|` 表示候选同义表达，禁含项有有限中文否定豁免；参考答案只用于人工对照，不提供给生成模型。

Agent 的工具名与参数严格匹配，也检查不需要工具时是否额外调用。40 条覆盖 RAG 8、订单工具 8、退款工具 7、不存在订单 4、HANDOFF 6、参数不足 3、对抗测试 4；预期路径为 RAG 8、TOOL 20、HANDOFF 12。不乱调用工具为 20/20。

V1.1 完整基线运行于 2026-10-20：40 条链路完成、80 次实际请求，API 失败与重试均为 0，没有排除决策指标分母。固定集表现不能外推到任意真实流量。

原始结果：[RAG 基线](../eval/results/baseline_v1_2/rag_eval_summary.json)、[Agent V1.1 基线](../eval/agent_v1_1/agent_eval_summary.json)。

## 4. V1 → V1.1：围绕失败做有限修改

| 调整 | 内容 |
|---|---|
| 实时查询优先级 | 有充分订单号时，“别查系统”“假装到账”等指令不能绕过工具，也不能仅转人工回避核验；仍由模型决定调用 |
| 临时故障重试 | timeout、429/500/502/503/504 最多额外重试两次，等待 1、2 秒；配置类错误不盲目重试，SDK 重试关闭 |
| 技术失败归类 | 未取得决策时，行为项记未评分并报告排除数量；整题及回答仍失败。已取得的行为评分保留 |
| 请求计数 | 区分实际尝试与逻辑调用，保留失败记录 |

| 指标 | V1 | V1.1 |
|---|---:|---:|
| 路径 | 38/40，95% | 40/40，100% |
| 工具选择 / 参数 | 各 19/20，95% | 各 20/20，100% |
| HANDOFF | 12/12，100% | 12/12，100% |
| 最终回答规则通过 | 35/40，87.5% | 39/40，97.5% |

没有同时更换知识库、模型、Top K、工具、测试集或回答匹配词表。AG-040 在 V1.1 已选对退款工具与参数，按尚未到账回答。分数变化还涉及请求可用性、统计口径与自然措辞，不能全部归因于 Prompt。重试通过离线故障注入验证，在线基线未触发重试。

## 5. 保留评分误判，而非为分数改变正确行为

**AG-006：** 回答说明无法确认烟酰胺比例、不能给出准确浓度，语义符合资料边界，但未命中固定候选表达，是 V1.1 全量中唯一自动失败题。原成绩保留，没有强迫模型复述固定句式或放宽规则。

**AG-040 首次五条复测：** 工具与未到账结论正确，但“不能确认已到账”被规则误读；全量运行换一种措辞后通过，两次结果均保留。这说明自动分数与业务语义需分别检查，不说明所有失败都是评分问题。

## 6. 展示与运行记录

Streamlit 主区展示问答，折叠详情显示真实路径、参考来源或工具参数/模拟结果及耗时。Session 复用服务、保留显示历史，但不传历史给模型；HANDOFF 不声称已接通人工。验证包括 AppTest 与浏览器人工验收。

CLI / 网页在实际请求结束后向 `logs/runtime.jsonl` 写一条摘要，rerun 不重复记录，写盘失败不影响原回答：

- 记录时间、请求 ID、入口、实际路径、正常返回状态和耗时；工具摘要包含必要订单号及真实 found/mock 标记，多工具放入同一记录。
- 错误记录固定安全摘要，不复制 traceback；异常未取得 AgentResult 时路径为 null，不猜测部分轨迹。
- `api_attempts` 是真实尝试数，包含重试；未知则省略，不等于 retry_count 或完整 API telemetry。`success=true` 不代表答案通过评测。
- 默认不存完整问答、preview、Prompt、知识正文、完整工具结果或密钥；日志不进 Git，没有轮转、告警或跨进程事务保证。

已有四次 UI 请求和一次 CLI 查询的日志验收，重绘不重复记录，权限/磁盘故障不破坏回答；离线测试 88 项通过。2026-10-31 另在临时副本用既有依赖和 BGE 缓存验证首次建库与检索，未改原库或重跑在线 Eval，范围见 [Running](RUNNING.md)。

## 7. 局限与后续方向

这是模拟业务 Demo：无真实平台、身份认证、订单授权、人工队列、写操作或多轮 Memory。检索来源只是参考，规则评分不覆盖完整语义；依赖未完整锁定，日志为尽力写入，不具备生产保障。

真实落地需另行解决授权接口、订单归属、人工工单及写操作确认，再用实际问题验证效果与风险。是否增加重排或混合检索，应由召回、排序与回答失败分析决定。以上均为未来方向，当前没有商业收益或生产部署证据。

项目展示的是从需求划分、受约束的模型工具调用、分层评测到 UI 与轻量观测的完整交付过程，核心判断是分清事实来源、操作权限和验证对象。
