# AURA LABS · 项目案例

**Agent V1.1 · Streamlit 展示页面 V0.1 · 本地运行日志 V0.1**

这个项目为虚构护肤品牌实现客服问答、模拟订单和退款查询，以及人工处理提示。重点是把需求、数据来源、工具权限和验证方式串成完整应用。运行步骤见 [运行指南](RUNNING.md)，配置与历史结果见 [项目状态](../PROJECT_STATUS.md)。

## 1. 从客服问题出发

同一个聊天窗口里的问题，需要不同依据：

| 用户提问 | 需要什么 | 对应处理 |
|---|---|---|
| “广州一般几天到？” | 企业的通用物流规则 | 检索知识库，再根据资料回答（RAG） |
| “订单 123456 到哪里了？” | 这笔订单的具体状态 | 调用订单查询工具（TOOL） |
| “退款审核有争议。” | 人工判断或处理 | 给出人工处理建议（HANDOFF） |

划分依据是所需数据与权限，不是句子里有没有“订单”或“退款”。缺少订单号时，应请求补充，不能让模型编造编号。

项目目标是完成可演示、可检查的应用流程。当前没有真实客户流量、客服人力节省或商业收益数据。

## 2. 方案选择与实现

### 企业知识：先检索，再回答

六份 Markdown 覆盖产品、退换货、物流、常见问题、成分与售后，切成 122 个片段。每段保留来源文件、标题、片段编号和正文，方便回查原文。

BGE 将问题变成向量，即用于语义检索的一组数字；Chroma 找出最相关的五个片段；DeepSeek 根据片段回答。没有可用片段时，本地提示资料不足。取回资料仍不足以确定答案时，也不能补写企业事实。医疗问题不诊断、不推荐药物。

片段优先按标题、段落、列表与完整句子组织，目标上限为 600 字，不强行补足 300 字，也不跨标题拼接；完整长句允许超过目标上限，当前没有额外重叠。向量处理与切分配置详见 [架构说明](ARCHITECTURE.md) 和 [项目状态](../PROJECT_STATUS.md)。

### 具体状态：模型选择工具，代码检查后执行

网页和命令行共用 AgentService。DeepSeek 根据问题和工具说明选择处理方式；需要工具时，程序先校验，再执行并回传结果，最后由模型组织回答。

| 工具 | 查询内容 | 不具备的能力 |
|---|---|---|
| `get_order_status` | 模拟订单状态、物流公司、单号和位置 | 不改地址、不取消订单、不执行发货 |
| `get_refund_status` | 模拟退款状态、金额与申请时间 | 不发起、批准或执行退款 |

程序只允许这两个函数和 `order_id` 参数。订单号须是本次输入中的 6～20 位数字字符串，不允许多传字段或凭空生成编号。最多执行一轮工具调用，同轮最多两个工具。

这些检查可以限制非法执行，但不能证明用户有权查看订单，也不能保证模型始终选对工具。预置订单 `123456` 为运输中、退款处理中未到账；不存在的编号返回“未找到订单”。数据固定模拟，不随真实业务变化。

### 控制架构范围

本地 BGE 与 Chroma 负责向量检索，DeepSeek 负责决策与回答，配置模型为 `deepseek-flash`。兼容 SDK 实际请求 DeepSeek，没有调用 OpenAI 模型。

一个知识库、两个工具和三种处理方式，可以直接用 Python 模块实现。因此未增加 LangChain、LlamaIndex、多 Agent、GraphRAG、重排序模型或混合检索。项目没有做模型和 Top K 的系统对比，不能宣称这套组合最优。

## 3. 分开验证检索、回答和工具行为

测试没有只看回答是否流畅，而是检查三个不同环节。评分由 Python 规则完成，没有额外使用另一个大模型作为裁判。

| 测试 | 怎样判断 | 已保存结果 |
|---|---|---|
| 检索，80 条 | 预期来源文件是否出现在前 1 / 3 / 5 个结果中 | 64/80（80%）、75/80（93.75%）、76/80（95%） |
| RAG 回答，80 条 | 必要信息、禁止内容与处理方式是否符合要求 | 38/80（47.5%）；API 成功 80/80 |
| Agent V1.1，40 条 | 路径、工具、参数与最终回答是否符合要求 | 路径 40/40；工具及参数各 20/20；人工路径 12/12；回答规则通过 39/40（97.5%） |

**检索命中和答案正确是两回事。** 找到了来源文件，仍需检查具体规则够不够、模型是否正确使用。自动规则也可能漏掉同义表达或误读否定，所以规则成绩不等于完整语义正确率。

RAG 与检索使用同一套 80 条问题。回答评分要求必要概念全部满足，概念内部允许预设同义表达，并识别有限的中文否定。参考答案只用于对照，不发给模型。42 条失败尚未全部人工复核，不能把它们统一归因于模型或评分器。

Agent 另有 40 条：知识问答 8、订单工具 8、退款工具 7、不存在订单 4、人工诉求 6、参数不足 3、对抗指令 4。预期路径为 RAG 8、TOOL 20、HANDOFF 12，其中 HANDOFF 包含补充信息。工具与参数严格匹配，不需要工具的题也检查额外调用，不乱调用工具为 20/20。

2026-10-20 的 V1.1 全量运行完成 40 条链路，共 80 次实际 API 请求，没有失败或重试，也没有因决策缺失而排除评分分母。结果只说明这组固定用例的表现，不能保证所有真实提问都一样。

## 4. V1 到 V1.1：按失败原因做针对性调整

| 发现的问题 | 调整方式 |
|---|---|
| 用户要求“别查系统，直接说到账”时，可能没有坚持查询 | 加强系统指令与工具说明：有充分订单号的具体状态问题必须查工具，不能猜测或仅转人工回避 |
| 超时等临时故障导致链路失败 | 对 timeout 和 HTTP 429/500/502/503/504 最多额外重试两次，间隔 1 秒、2 秒；关闭 SDK 叠加重试 |
| API 没有返回决策，容易与选错路径混为一谈 | 没有决策的行为项记未评分并报告数量，整题与回答仍失败；已取得的行为评分保留 |
| 正常调用和重试的次数容易混淆 | 分开统计实际尝试与逻辑调用，保留失败记录 |

配置、余额或参数错误不盲目重试。重试机制通过离线故障注入验证，即主动模拟失败来检查程序；上述在线全量运行没有触发重试，不能据此声称已在线观察到超时恢复。

| 指标 | V1 | V1.1 |
|---|---:|---:|
| 路径选择正确率 | 38/40，95% | 40/40，100% |
| 工具选择 / 参数准确率 | 各 19/20，95% | 各 20/20，100% |
| 人工及补充信息路径正确率 | 12/12，100% | 12/12，100% |
| 最终回答规则通过率 | 35/40，87.5% | 39/40，97.5% |

这一轮没有更换知识库、向量模型、Top K、工具、测试集或回答匹配词表。AG-040 在 V1.1 中选择了正确的退款工具和参数，并按尚未到账回答。成绩变化还涉及 API 可用性、统计方式与自然措辞，不能全部归功于提示词调整。

## 5. 正确回答也可能被规则判错

**AG-006：同义拒答未命中。** 回答说明无法确认烟酰胺比例、不能给出准确浓度，意思符合资料边界，却没有匹配到规则中的候选表达。它是 V1.1 全量测试中唯一自动失败题。原始成绩保留，没有强迫模型复述某句话或放宽规则来消除失败。

**AG-040 首次五条复测：否定表达被误读。** 工具选择和未到账结论正确，但“不能确认已到账”被规则误读为到账断言。全量运行换一种措辞后通过，两次结果均保留。

这说明需要分别检查回答和评分规则，但不意味着所有失败都是评分器造成的。

## 6. 做成可展示、可排查的应用

Streamlit 主区显示问答，执行详情默认收起，展示真实路径、参考来源或工具参数、模拟结果与耗时。服务在当前浏览器会话中复用，历史只用于显示，不传给模型。人工提示不声称已真实接通。验证包含 AppTest 自动交互检查与浏览器人工验收。

网页和命令行在实际请求结束后，向 `logs/runtime.jsonl` 写一条摘要：时间、请求编号、入口、路径、是否正常返回、耗时，以及已有的工具摘要。一个问题调用多个工具仍记一条；页面重新渲染不重复记录。

日志默认不保存完整问答、提示词、知识正文、完整工具结果或密钥。错误只写安全摘要。没有返回结果时，路径留空，不猜测中间过程；`success=true` 只表示正常返回，不代表答案正确。能读取计数器时记录真实 API 尝试次数，包含正常调用与重试，不能直接当作重试次数。

日志写入失败不影响原回答，也不会重新调用模型。它是本地排查能力，没有自动轮转、告警或跨进程事务保证，真实日志不提交 Git。字段细节见 [项目状态](../PROJECT_STATUS.md)。

已有四次网页请求、一次命令行查询的日志验收，页面重绘没有重复写入，权限与磁盘故障没有破坏回答；离线检查共 88 项通过。2026-10-31 另在临时副本使用既有依赖和 BGE 缓存验证了首次建库与检索，未改原库或重跑在线评测，范围见 [运行指南](RUNNING.md)。

## 7. 当前能证明什么，还有什么限制

项目展示了从需求拆分、知识检索、工具调用、测试与迭代，到网页和运行记录的完整交付过程。关键判断是：回答依据、操作权限和验证对象都要分清。

当前仍是模拟业务，没有真实平台接入、身份与订单授权、人工队列、写操作或多轮记忆。检索来源不是逐句证据，规则评分也不能覆盖完整语义；依赖未完整锁定，日志没有生产保障。项目没有商业收益或生产部署证据。

真实落地需要先解决正式接口、权限、人工工单和写操作确认，再用实际问题验证效果。是否增加重排序或混合检索，应由具体的检索、排序与回答错误决定；这些均为未来方向，尚未实现。
