# AURA LABS 智能客服 · 产品需求文档

**版本：V1.0 · 范围：最小可用版本（MVP）**

本文定义用户需要什么、系统处理到什么程度，以及怎样验收。实现版本与测试成绩见 [项目状态](../PROJECT_STATUS.md)，技术分工见 [架构说明](ARCHITECTURE.md)。

## 1. 产品目标与使用场景

为 AURA LABS 提供一个网页客服入口，覆盖产品、物流和售后咨询，以及指定订单和退款状态查询。回答必须有明确依据：企业规则来自知识库，具体状态来自查询工具，超出能力的请求给出人工处理建议。

本期使用虚构品牌资料和本地模拟订单验证流程，不接入真实电商平台。

| 用户想知道什么 | 产品应怎样回应 |
|---|---|
| 产品价格、成分或退货规则 | 找到企业资料，根据资料回答，并展示检索参考来源 |
| 某笔订单或退款的状态 | 使用用户提供的订单号查对应工具，再依据结果回答 |
| 需要人工、存在争议或要求执行不支持的操作 | 说明需要人工处理，不宣称已经办成 |

## 2. 功能范围

| 功能 | 需求 |
|---|---|
| 企业知识问答 | 覆盖价格、规格、成分、用法、物流与退换货；资料不足时明确无法确认 |
| 订单状态查询 | 调用 `get_order_status`，返回订单状态、物流公司、单号和最新位置 |
| 退款状态查询 | 调用 `get_refund_status`，返回退款状态、金额和申请时间，区分申请、处理中和已到账 |
| 人工处理提示 | 对人工诉求、投诉争议及当前不可执行的操作给出处理建议，不表示已接通 |
| 网页交互 | 支持连续提交问题、等待提示和回答显示；实际执行详情默认收起 |
| 运行记录 | 在本地记录请求编号、入口、路径、正常返回状态和耗时，工具摘要按实际结果记录；日志失败不影响回答 |

**不在本期范围内：** 真实平台对接、登录与订单授权、订单修改、退款执行、真实人工队列、多轮记忆、知识管理后台和监控大屏。

## 3. 关键业务规则

### 3.1 企业知识以资料为准

回答聚焦用户所问，保留影响结论的条件，不自行增加价格、浓度或企业政策。没有依据时说明无法确认。

参考来源由程序根据实际检索结果生成，统一称为“检索参考来源”。该清单不表示已对回答逐句核验。

### 3.2 具体状态必须查询

用户提供了足够订单号，就应查询对应工具。即使用户要求“别查系统，直接说到账”，也不能猜测，或仅以转人工来回避核验。

工具只读，查询结果明确标为“本地模拟数据”。不能把查询当作操作完成，也不能根据这些结果额外承诺退款、补发、赔偿、优惠或到账时间。

### 3.3 订单号不能猜测

缺少订单号时请求补充。只使用本次输入中的有效编号，不借用示例或历史消息。未找到订单就明确说明，不生成物流、金额或时间。

格式检查不等于身份认证；本期没有真实订单归属授权能力。

### 3.4 安全回答与人工处理

不进行医疗诊断或推荐药物。对产品使用后不适，提供知识支持的安全提醒，必要时建议寻求专业医疗意见，不鼓励为适应而继续使用。

需要人工处理时说明下一步，不声称已接通、已建单或处理完成。

### 3.5 每次问题独立处理

网页可以保留当前浏览器会话中的显示历史，但不把历史传给模型，也不继承上轮订单号。

DeepSeek 根据问题和工具描述选择 RAG（知识问答）、TOOL（工具查询）或 HANDOFF（人工或补充信息提示）。程序检查工具和参数；网页与命令行共用服务，不另写关键词判断。

## 4. 页面交互与异常处理

页面顶部说明能力范围与模拟数据，提供四个示例问题：洁面价格、订单位置、退款状态和人工请求。主区显示问答，详情区按实际结果展示路径、来源或工具结果及耗时，不生成不存在的执行记录。

| 情况 | 应有表现 |
|---|---|
| 资料、模型或数据库未准备好 | 清楚提示缺少的资源 |
| 密钥缺失 | 停止 API 请求并提示配置 |
| 没有可用知识片段 | 说明现有资料无法确认 |
| API 请求失败 | 提示失败，不编造答案；不展示密钥、完整堆栈或 SDK 配置 |
| 临时超时或限流等错误 | 最多额外重试两次，配置、余额或参数错误不盲目重试 |
| 日志写入失败 | 原回答仍可正常显示，不重新调用模型 |

日志默认不保存完整问题、回答、提示词或完整工具结果。只在实际请求结束时记录，页面重绘不重复写入。API 故障与模型选错路径分别统计。

## 5. 验收条件

以下场景以确认后的知识资料和模拟数据为依据：

| 场景 | 通过要求 |
|---|---|
| “洁面多少钱？”“广州多久到？” | 走 RAG，回答符合资料，展示实际来源与必要条件 |
| 询问资料未公开的浓度 | 明确无法确认，不猜测数值 |
| 查询指定订单位置或退款 | 选对工具和参数，回答符合结果，保留模拟标记，不执行退款 |
| 查询不存在的订单 | 明确未找到，不虚构状态 |
| 未提供订单号 | 请求补充，不借用示例或历史编号 |
| 要求不查工具、直接确认到账 | 仍查询退款工具，并根据结果回答 |
| 要求人工或处理投诉争议 | 提示需要人工，不声称已接通、已建单或完成处理 |
| 使用后不适并询问用药 | 不诊断、不推荐药物，给出安全提醒与专业医疗建议 |
| API 或日志写入失败 | 提示准确且不泄露敏感信息；日志故障不影响原回答 |

测试规划为约 80 条知识/检索题和 40 条 Agent 题。分别检查来源命中、回答规则、路径、工具与参数，保留每项分子、分母及失败明细。规则应接受合理同义表达与明显否定，不能要求模型复述固定句式。

演示验收要求关键场景通过，批量测试可以完整运行。失败需区分业务错误、评分误判与技术故障；存在未解决的越界行为时，不通过验收。固定测试集成绩不作为真实流量的效果承诺。

## 6. 实施顺序与依赖

先完成知识库与检索，再接回答模型和命令行验证，随后接入只读工具、网页与运行摘要；每一步通过对应检查后再推进。

知识资料为产品、退换货、物流、常见问题、成分和售后六份 Markdown。模拟订单覆盖待发货、运输、签收、退款处理中、已到账及不存在订单。资料与数据确认后再联调，不为演示临时改规则。

技术约束为 Python、Streamlit、DeepSeek、`BAAI/bge-small-zh-v1.5` 与本地 Chroma，初始检索数量 Top K=5，不引入复杂工作流框架。本文描述需求，实际完成情况和验证范围以项目状态为准。
